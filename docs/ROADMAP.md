## 1. สนามที่เลือก และเหตุผล

> 🔴 **แก้ไขจากฉบับ 10 ก.ย.** — ฉบับแรกเสนอให้ยิง Paper Track เป็นสนามเดี่ยว **ข้อเสนอนั้นผิด**
> การสืบกติกา (ดู `competition-brief.md` §2, §8) พบว่า **Paper Track ยืนอิสระไม่ได้ ต้องมี
> ARC-AGI-3 submission ที่รันได้จริงก่อน** ลำดับงานจึงถูกบังคับ: **code ก่อน → paper อ้างถึง code นั้น**

ARC Prize 2026 มี 3 สนาม:

| สนาม | เงินรางวัล | ลักษณะ | สถานะ |
|---|---|---|---|
| **ARC-AGI-3** | $850,000 | code competition — เกมเชิงโต้ตอบ (agentic) | **สนามหลัก** |
| **Paper Track** | $450,000 | Kaggle Writeup ~1,500 คำ + cover image + public notebook | **ต่อยอดจาก ARC-AGI-3** |
| ARC-AGI-2 | — | code competition — ปริศนา grid | ไม่เลือก (SOTA 24%, ทีมสะสมมาหลายปี) |

**แผน: ทำ ARC-AGI-3 ให้มี submission ที่รันได้ แล้วเขียน Paper Track ต่อยอด**

เหตุผลที่ยังคุ้มแม้ต้องทำ code:

1. **เพดานต่ำมาก** — Milestone #1 ชนะด้วย **1.21%** และ high score ปัจจุบัน **7.51%** ต่างจาก ARC-AGI-2 ที่ SOTA 24%
2. **Paper ไม่ใช่งานใหญ่อย่างที่คิด** — 1,500 คำ ไม่ใช่เปเปอร์วิชาการเต็มรูป (PDF เป็น optional)
3. **5 ใน 6 เกณฑ์ให้คะแนน paper ไม่ขึ้นกับ leaderboard** — คะแนน code ต่ำไม่ปิดโอกาส paper prize
4. **Bonus $375K เป็น threshold ไม่ใช่การจัดอันดับ** — เกิน 4.5/5 แล้วแบ่งเท่ากันทุกคนที่ผ่าน ไม่ต้องชนะใคร
5. **มี reference ที่ชนะจริงให้ศึกษา** — โซลูชัน Milestone #1 เปิด source แล้ว

## 1b. ข้อจำกัดที่ต้องออกแบบรอบ (สำคัญที่สุด)

1. 🔴 **Internet ปิดระหว่าง scoring** → **สถาปัตยกรรมที่เรียก external LLM API ส่งไม่ได้**
   เหลือ: local weights แพ็กมากับ notebook / โปรแกรมแบบ non-neural / ลูกผสม
   **ต้องตัดสินใจก่อนเขียนโค้ดบรรทัดแรก**
2. 🔴 **ผู้เยาว์** — อายุบรรลุนิติภาวะไทย = 20 ปี และ Kaggle ใช้ "ค่าที่มากกว่า" ระหว่าง 18 กับเกณฑ์ท้องถิ่น
   → ต้องผ่านเส้นทาง parental/guardian consent และเมื่อชนะ **ผู้ปกครองต้องลงนามภายใน 7 วัน**
   **เตรียมเอกสารล่วงหน้า ไม่ใช่รอตอนประกาศผล**
3. **ต้อง open source ภายใต้ CC0 หรือ MIT-0** ก่อนได้รับคะแนน private evaluation (MIT-0 ≠ MIT)
4. **Scoring ลงโทษ action เกินจำเป็นแบบกำลังสอง แต่ internal reasoning ฟรี** → ออกแบบให้ "คิดหนัก กดน้อย"
5. **Competition mode คิดคะแนนทุก environment ไม่ว่าจะเล่นหรือไม่** และโต้ตอบได้ครั้งเดียวต่อ environment
   → การจัดสรร budget ข้ามเกมเป็นปัญหาที่ต้องแก้ เกมที่รันไม่ทัน = 0

**สภาพแวดล้อม:** Python **3.12** (บังคับ), ไม่ต้องใช้ GPU สำหรับ starter agent, package manager คือ `uv`

> รายละเอียดและแหล่งอ้างอิงทุกข้อ: `docs/competition-brief.md`

## 2. กติกาเหล็ก (สืบทอดจาก EcoSync)

> **ห้ามมโนตัวเลข — ทุกตัวเลขต้องวัดจริง + บอกที่มาได้**

ในบริบท ARC แปลว่า:
- คะแนนทุกตัวต้องมาจาก `arc eval` ที่รันจริง ไม่ใช่ประมาณเอา
- แยก **training** (ใช้พัฒนา) ออกจาก **evaluation** (ใช้วัดผลสุดท้าย) เด็ดขาด
- ห้าม tune บนชุด evaluation ซ้ำ ๆ แล้วรายงานคะแนนนั้น (เป็น data leakage — ประเด็นเดียวกับที่แก้ในเล่ม EcoSync)
- บันทึกทุกการรัน: solver, split, วันที่, commit hash

## 3. ตารางงาน

### Phase 0 — พื้นฐาน ✅ เสร็จแล้ว
ตัวโหลด + ตรวจข้อมูล 1,120 task, CLI `verify`/`stats`/`show`, เทส 19 ตัว

### Phase 1 — วัดผลให้ได้ (10–24 ก.ย. · 2 สัปดาห์)
เป้าหมาย: **มีตัวเลขจริงตัวแรก**

| # | งาน | ผลลัพธ์ |
|---|---|---|
| 1.1 | Evaluation harness ตามกติกาจริง (2 attempts, exact match, ต้องถูกทุก test input) | `arc/evaluate.py` + `arc eval` |
| 1.2 | Baseline solvers ชุดกฎ (identity, tiling, สมมาตร, map สี ฯลฯ) | `arc/solvers/` + คะแนนวัดจริง |
| 1.3 | วิเคราะห์ข้อมูล: taxonomy ของการแปลง, ความสัมพันธ์ขนาด in→out | `docs/dataset-analysis.md` |
| 1.4 | สืบกติกาแข่ง: ข้อจำกัด compute, ต่อเน็ตได้ไหม, รูปแบบ submission, ผลปี 2025 | `docs/competition-brief.md` |

**ตัวชี้วัด Phase 1:** รัน `arc eval --solver <name> --split evaluation` แล้วได้ตัวเลขที่เชื่อถือได้

> คาดการณ์ล่วงหน้าอย่างซื่อสัตย์: baseline แบบกฎจะได้ **ใกล้ 0%** บน evaluation — มนุษย์ยังได้แค่ 66% นี่ไม่ใช่ความล้มเหลว แต่คือเส้นฐานที่ต้องมีเพื่อพิสูจน์ว่าอะไรได้ผลจริง

### Phase 2 — สร้าง solver จริง (25 ก.ย. – 15 ต.ค. · 3 สัปดาห์)
ขึ้นกับผล Phase 1.4 (ถ้าแข่งห้ามต่อเน็ต แนวทาง LLM API จะใช้ได้เฉพาะใน paper เท่านั้น)

- 2.1 **LLM solver** — ส่ง task ให้โมเดลผ่าน Claude API + prompt ที่มีโครงสร้าง, verify คำตอบกับ train pairs ก่อนตอบ
- 2.2 **Program synthesis / DSL** — ค้นหาโปรแกรมสั้น ๆ ที่อธิบาย train pairs ได้ครบ แล้วใช้กับ test
- 2.3 **Hybrid** — ใช้ LLM เสนอสมมติฐาน แล้วใช้ DSL ตรวจสอบ (นี่คือมุมที่น่าเขียนลง paper ที่สุด)
- 2.4 วัดผลทุกตัวด้วย harness เดียวกัน บันทึกทุกการรัน

### Phase 3 — วิเคราะห์ (16–31 ต.ค. · 2 สัปดาห์)
- 3.1 **Ablation** — ถอดทีละส่วนเพื่อดูว่าอะไรทำให้คะแนนขึ้นจริง (แบบเดียวกับ §4.1 ของเล่ม EcoSync)
- 3.2 **Error analysis** — จัดกลุ่มว่าพลาดแบบไหนบ้าง
- 3.3 ล็อกตัวเลขสุดท้าย ห้ามแก้หลังจากนี้

### Phase 4 — เขียนและส่ง (1–8 พ.ย. · 1 สัปดาห์)
- 4.1 เขียน writeup (โครง: ปัญหา → แนวคิด → วิธี → ผลวัดจริง → ablation → ข้อจำกัด)
- 4.2 ตรวจทาน, ตรวจตัวเลขทุกตัวย้อนกลับไปหา log การรัน
- 4.3 **ส่ง ≤ 8 พ.ย.** (เผื่อ 2 วันกันเหตุสุดวิสัย — deadline จริง 10 พ.ย. 06:59)

## 4. ความเสี่ยงที่รู้ตัวแล้ว

| ความเสี่ยง | การรับมือ |
|---|---|
| แก้โจทย์ไม่ได้เลย (คะแนน 0%) | Paper Track ให้คุณค่ากับแนวคิด+ความซื่อสัตย์ ไม่ใช่คะแนนล้วน — รายงาน 0% พร้อมวิเคราะห์ว่าทำไม ยังเป็น paper ที่ดีได้ |

| ชนกับ deadline อื่นของนักเรียน | Phase 4 เผื่อกันชนไว้ 2 วันแล้ว |
